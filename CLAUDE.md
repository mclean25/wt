# wt — for Claude

Personal git-worktree TUI. Single developer, single machine, OSS-published. Bun + React + OpenTUI on top of TanStack Query.

## Workflow

Commit and push directly to `main`. Don't create feature branches, don't open PRs, don't suggest either — unless the user explicitly asks. This is a single-developer repo and the feature-branch dance is pure overhead here. When in doubt, stay on `main`.

## Architecture (rules; map in docs/architecture.md)

- Three layers — sources (`src/state/queries/`), rows (`src/tui/rows/`), driver (`src/tui/panels/details.tsx`). Rows are pure-presentational; fetching stays in sources. Don't cross the boundaries.
- `src/tui/app.tsx` is the composition root and only routes; new flow logic goes in `src/tui/flows/`, new modal keys in `src/tui/modal-keys/`, not back into app.tsx. Keyboard dispatch order (modal → footer input → removed view → `h` → normal) and the handler order inside `normal-keys.ts` are load-bearing.
- Big core modules are directories behind same-named flat barrels (`core/github.ts` → `core/github/`, …); only names re-exported by the barrel are public, and importers use the flat path. Per-harness code lives under `core/harness/<harness>/` behind the `Harness` interface.
- `src/core/config.ts` defines the config contract (fail-fast loader, optional sections `null` when absent, `requireSst()` for SST-only paths). Read the stable-files list in docs/architecture.md before touching contract files.
- **A CLI command imports only what it needs — `cli/index.ts` is a map of lazy `() => import(...)` loaders, never static imports.** Users update hot from main, so any push can put a broken module in front of every agent on the machine; static command imports meant one bad export took out all 21 subcommands at once, including the `wt status` an agent uses to say it's stuck. The same rule applies *inside* a command whose branches have different needs: `wt manager report` writes a spool file and imports no session machinery, precisely so the fleet can still report that delivery broke. Not importing statically costs nothing — tsconfig has no `include`, so `tsc --noEmit` type-checks every module regardless of who imports it. Verify with `scripts/broken-module-check.sh`, which breaks a leaf module in a throwaway copy and prints which commands survive.

## Working principles

- **Only encode facts that are write-once and self-expiring.** A field that needs upkeep will drift, and a drifted field is worse than prose — prose is visibly dated, a field looks authoritative. Corollaries: bundle new state onto an existing mandatory step rather than minting a command or prefix ritual (rituals get forgotten — the `wt run --managed` rejection); close the hole in the tool over teaching agents a habit (the destroy reaper, `gh-merge-base` at create); assign ownership to whoever holds the knowledge first-hand, never to the relay; absence of a value means "unknown", never "fine". Worked rejection: a fleet-level decision queue — nothing would close its items automatically, so it would rot into a hand-maintained list; the `ready` notes already carry that information. Worked acceptance: merge edges (`core/merge-edges.ts`) — pairwise assertions that decay the moment either branch moves; and dev-server slots (`core/dev-server.ts`), where a slot is *held by a live tmux session* rather than counted, and the queue is one file per waiter carrying its pid, discarded by the next reader once that pid is gone. Both have the same tell: there is no release call to forget, so a SIGKILL can't corrupt the accounting.
- **Offload the human, always.** wt exists to shrink human involvement to the parts only a human can do — merges, logins/credentials, judgment calls, risk acceptance. Everything agents are good at, and everything deterministic code can do, moves to agents or into wt itself. This is top of mind for EVERY changeset: when building, apply it automatically (don't add a manual step where a watcher, an automation, a status assertion, or a manager briefing could absorb it); when designing, actively propose moving existing human work to agents or code. The intent doc is docs/fleet.md — read it before status/manager/automation-shaped work, and update it in the same commit when a change moves the human/agent boundary.
- **Source fetches stay batched, which means never PER ROW — not "one HTTP request".** The github source aliases every per-worktree PR field plus the repo `mergeQueue` block into one query doc, and new PR fields go into `PR_FRAGMENT` in `core/github/fetch.ts` rather than getting their own query. But that doc is split across fixed-size chunks (`CHUNK_SIZE`, 8 branches), because the invariant as originally written knew about only one of the two ceilings. Rate limits are metered in GraphQL *points*, computed from node count — so splitting is free, and measured free: the same 24 branches cost 27 points as one request and 27-28 across four. Server-side EXECUTION TIME is the other ceiling, it is about ~10s per query, and this query costs ~250ms per branch — so 24 branches took 6.9-7.7s and a fleet at 35 sat on it, producing 126 of one day's 130 failures at exactly `branchCount: 35` (502/504/"couldn't respond in time"/stream CANCEL) with 2184 of 5000 points unspent. **The tell that the wrong ceiling is being blamed is that the obvious fixes are all backwards**: throttling our side means fewer, larger, less frequent requests, which is the direction that fails; and field-trimming can't rescue it because no single field dominates (dropping the most expensive one takes 7.5s to 6.1s, and scalars alone still cost 2.2s). A latency cliff reads as intermittent flakiness right until nearly every request fails.
- **A chunked fetch fails whole or not at all.** `fetchGithub` retries an individual chunk on transient failure (5xx, GitHub's own timeout copy, an HTTP/2 CANCEL, a truncated body — four costumes for one event) and **never** on a rate limit, since retrying is what escalates a brush with the limit into a block. If a chunk still fails, the whole fetch throws: partial data is worse than none here, because a chunk that fails while its siblings succeed blanks the PR badge on exactly its branches, which is indistinguishable from "those branches have no PR" — the same lie an empty success tells, but per-row and therefore silent. Throwing keeps the last good cache for every row. Retries live in `core/github/fetch.ts`, not at the observer, so only the failed chunk re-runs and the CLI callers plus the webhook daemon inherit them; the TUI's global `retry: false` stays right for anything a keystroke drives.
- **A debounce is not a rate limit, and an unbounded fast path hides that it isn't.** The webhook daemon coalesced deliveries on a 1.5s debounce, which bounds a *burst* and bounds nothing at all under a *stream*: the trailing re-run after a burst landing mid-fetch went straight back into `runFetch`, so the cadence was set by query latency rather than by any policy. Measured on 18 branches with a merge queue running CI, 130 deliveries in 180s produced 13 full refetches at ~30 GraphQL points each — 7,760 points/hour against a 5,000/hour limit, on track to exhaust the budget before its reset, with nothing failing and nothing in the log to say so. Note the shape of the fix, because the two halves are load-bearing together: `MIN_FETCH_INTERVAL_MS` floors the rate measured from the previous fetch's START (so a slow query eats into the floor instead of adding to it), and routing the trailing re-run through the scheduler is what finally ARMS a starvation bug the debounce had carried all along — re-arming on every delivery defers the fetch indefinitely when deliveries arrive closer together than the debounce window, which at this fleet's measured ~43/min simulates to 151s and climbing. Hence `nextFetchAt` refuses to push out an already-pending timer. The floor costs no responsiveness because of WHICH fetch it delays: only the Nth of a burst, never the first after a quiet spell, which is the one that governs how fast a badge flips after a push.
- **`statusCheckRollup` is HISTORY; `mergeStateStatus` and `gh pr checks` are STATE.** GitHub keeps every check run recorded against a head sha forever, so a context that failed and was re-run green leaves BOTH entries under the same name. Read undeduped — which `rollupChecks` did — one superseded failure pins the checks badge red for the life of the branch, on a PR whose `mergeStateStatus` is CLEAN and whose `gh pr checks` shows 13 pass / 0 fail. The producing shapes are ordinary (a retried flake, a cancelled run, a job gated on `!draft` that failed before the PR was marked ready), the PR can never come back green on its own, and the remedy it pushes an agent toward is the worst one available: an empty commit to move the sha, spending a CI run to silence a false alarm. Note that fixing the WORKFLOW that produced any one red run does not touch the class. The derivation collapses to the newest run per context (`latestPerContext`, shared by `rollupChecks` and `failingCheckNames` so a named failure and a red badge can never disagree), which is why the query fetches `startedAt`/`createdAt` at all. **Where the timestamp is missing the entries are all kept**, preserving any-failure-counts: unknown ordering has to fail toward red, because a false red costs a look while a false green is a broken branch reported as fine.
- **AI summary is hash-keyed.** `aiSummaryQuery`'s queryKey is `["aiSummary", <hash>]`; equivalent diffs across rebases/amends/renames hit the same entry. "Previous summary stays visible while a new hash fetches" comes from `placeholderData: keepPreviousData` at the observer — no mismatch effect, no force-regen flag; the hash flipping IS the trigger. `refreshAiSummary` (`t`) refetches the diff context and `removeQueries` the entry for the resulting hash.
- **Pluginify reactively.** Built-ins now, plugins only when there's a second concrete implementation that justifies the seam. Don't pre-design for "what if someone wants Jira."
- **No client-app defaults in code.** `paths.main_clone`, `paths.worktree_root`, `branch.prefix` are required and the loader refuses to start without them. New required fields go through `Errors.reqStr`; add a derivation when one's natural (see `stage.prefix` defaulting from `branch.prefix`).
- **Errors render verbatim, gated on retries-exhausted.** `firstError` in `details.tsx` already handles the gate (`error && !isFetching`) — don't duplicate it elsewhere. The same error showing on every row that depends on a broken source is intentional.
- **Convention over configuration for the niche stuff.** `branch.id_pattern` exists but most users will never set it; the default matches Linear/Jira/Shortcut conventions.
- **Stacks are inferred, never stored.** The per-slug fork-base record (`baseBranch` + `baseSha` in wtstate) is the ONLY stack state; grouping, diff bases, and the restack engine all derive from it (`core/stack-layout.ts` infers, `core/stack-ops/` replays). Don't add stack registries, manifests, or membership caches — and never drop a `baseSha` when rewriting a record's branch: it's the squash-safe replay anchor (see docs/stacked-prs.md). The record is written for **trunk** forks too, even though they're stacked on nothing — every reader normalizes `baseBranch == trunk` to "no parent", and the anchor's second consumer is `forkBaseIsVacuous`, which needs it to tell an unstarted branch from a landed one.
- **"Merged" is a claim about work, not about reachability.** `branchIsMerged` gates containment on the branch having commits of its own since its recorded fork base (`baseSha`), because "every commit is on trunk" is vacuously true for a branch that added none — and that population is precisely every stacked worktree between `wt new` and its first commit. Left ungated it cost two GitHub issues, closed autonomously, describing work nobody had started. Any new predicate that means "this landed" carries the same guard, and anything that writes OUTSIDE wt off the back of one (`builtin:close-issue`) narrates on `log.attention.*`, since wt's undo doesn't reach there and the board shows nothing.
- **"Merge when ready" is TWO GitHub features wearing one label, and they are gated on different settings.** A base branch with a merge queue is enqueued (`enqueuePullRequest`); everything else arms classic auto-merge (`enablePullRequestAutoMerge`). Classic auto-merge requires the repo's "Allow auto-merge"; a queue does not — so on a repo with `allow_auto_merge: false` and a queue on `staging`, the GitHub UI cheerfully offers the button while wt's classic mutation returned `Auto merge is not allowed for this repository`. The report reads as a wt bug against a working GitHub feature, which is the wrong end to start from. `enableAutoMerge`/`disableAutoMerge` dispatch on the PR's `baseRefName`, and the cancel half matters as much: `--disable-auto` does NOT dequeue, so it would have reported success while the PR stayed queued and merged anyway. **And a merge queue belongs to a BRANCH, not a repo** — the unqualified `mergeQueue` GraphQL field resolves to the DEFAULT branch, so a repo queueing on `staging` while defaulting to `main` returned null on every poll and the position badge could never render. That failure is invisible in exactly the way that matters: an empty queue and the wrong queue are the same empty map, so the feature reads as "nothing is queued" forever. The fetch passes `branch.base` explicitly.
- **A mutation RESOLVING is not the server SERVING it, and the settling invalidate is aimed straight at the gap.** GitHub's GraphQL reads lag its own writes by a beat, so `runOptimisticMutation`'s `onSettled` refetch routinely lands pre-mutation data — the badge flips back to the value the user just changed and self-corrects seconds later on the next fetch, which reads as "it didn't work" and is the exact opposite of what an optimistic patch is for. Worst on the mutations with a webhook behind them, because each extra fetch is another chance to land stale. Releasing the clobber guard when `run` resolved was therefore half a guard: it covered concurrent refetches and not the one the mutation itself triggers. It now runs until a fetch arrives that the patch no longer CHANGES (structural compare, since `patch` builds fresh objects and is never `===` its input), or the mutation failed, or `SETTLE_GUARD_MS`. The catch-up condition is the real one and it must self-terminate, or a genuine later change by someone else gets suppressed; the deadline is only a backstop for patches the server will never echo — arming merge-when-ready on a queue base leaves `autoMergeRequest` null forever and surfaces as a queue entry instead. Any new backend whose reads lag its writes inherits the same shape.
- **"Merge when ready" fails DIFFERENTLY when the PR isn't ready, and the queue's refusal is the case the keystroke exists for.** A merge queue will not accept a PR whose required checks have not reported (`Pull request 2 of 4 required status checks have not succeeded: 1 expected.`) — which is exactly the window a user presses `! m` in. So `enableAutoMerge` tries `enqueuePullRequest` first (the ready case still gets a POSITION back, not just a flag) and falls back to `enablePullRequestAutoMerge` on that one refusal, which is GitHub's own "arm it and queue it when the requirements are met". The classifier (`notYetEnqueueable`) fails CLOSED and is matched on prose because it has to be: every enqueue refusal is GraphQL type `UNPROCESSABLE`, so "not ready yet" and "expected head oid does not match the current head oid" are the same error code, and treating the second as retryable would arm a merge for a commit the user never saw. Note the fallback is not universally available — a repo with `allow_auto_merge: false` (measured on the fleet's) refuses the classic arm outright, so both errors are reported together rather than just the second, which would send the reader to the wrong setting.
- **Mutating GitHub state? Invalidate `["github"]`, not the worktree.** Write-path `gh` calls must trigger `refreshGithub()` from `state/hooks.ts`. `invalidateWorktree(slug)` looks plausible but the github query is keyed by branch list, not slug — it silently misses.
- **Automations are level + ledger, never edge-triggered.** The `[[automations]]` engine (`core/automations.ts` ledger, `tui/automation-rules.ts` pure evaluation, `tui/hooks/useAutomations.ts` queue + dispatch) re-derives conditions from row state every pass; once-only comes from persistent fire keys keyed on head SHA. Hard rules: `markFiresDispatched` runs synchronously before any await in a dispatch; PR-driven conditions require `githubFresh` plus `pr.headRefOid` (persisted-cache data must never fire); failures mark delivered and never retry (new SHA = the retry); the per-(rule, target) breaker trips after `BREAKER_LIMIT` consecutive no-clear dispatches and resets only when the condition is observed false. New triggers: add to `AutomationTrigger` in config.ts + a case in `automation-rules.ts` with a documented fire key. Runs dispatch through the same paths keystrokes use, never bespoke ones. Semantics doc: docs/automations.md.
- **An automation that briefs a session must not fire on that session's own write.** The needs-human briefing's audience is the manager, and the manager's LAST triage step is sharpening the note it was briefed about — a re-assertion, so a new `at`, so a new fire key, so another briefing quoting its own words back. It fired three times for one slug and the honest answer to the third was "nothing changed"; a briefing whose usual correct answer is "nothing changed" stops being read, which spends the only channel that says "a worktree is blocked on the human". The general shape: **a trigger derived from a WRITE is reflexive in a way a trigger derived from observation never is** — every other condition here comes from git/GitHub, which no session can assert. So a fire needs to know its audience (`ctx.audienceOf` → the action's `target`) and the record needs to know its author (`WorkStatusRecord.by`, from the `WT_AGENT` stamp — one definition in `core/agent-identity.ts`, shared with the fleet-mail sender tag). Note which way it fails open: an UNATTRIBUTED record (the `u` picker, a plain shell, anything written before `by`) is not the audience and still fires, because "unknown" must not silently swallow a real escalation.
- **A coordinator's memory is not storage, and the tell is that it survives one compaction and no more.** A fleet sweep held fourteen worktrees back on an unlanded credentials file with the policy living in section NAMES it had invented ("Held: prompt written, deliberately not started") plus its own recollection of which gate applied to which row and what would clear it. A section name says something is held; it cannot say what would unhold it. Two fields came out of that retrospective and both obey the write-once-and-self-expiring rule, which is why they were safe to add: `--blocked-on` widened to `todo` (deliberately not STARTED, versus `ready`'s do not MERGE — the field names the external condition and the STATE supplies the verb), and `WtSlugState.examined`, a verdict stamped with the sha it was reached at. The second is the sharper design: it is a SKIP HINT and never authority, so absent/stale/unrecognised all mean "look properly" and the failure direction is wasted work rather than a missed row — and it voids itself when the branch moves, which is exactly when a conclusion stops being trustworthy. It is deliberately NOT part of the work-status record: a status is what the row's OWNER claims, a verdict is what an OBSERVER concluded, and collapsing them loses which is which. What it bought, measured: one sweep ran the same two-call review query against the same two PRs on four consecutive passes for the same empty answer, because a review job reports failed while its review is still running.
- **A recurring prompt is a snapshot, and it decays faster than the interval.** An external cron set up to shepherd the fleet had to be torn down and recreated three times in an hour — never because the schedule was wrong, always because a STANDING FACT baked into its prompt had gone stale ("suite X is red on the mainline", retracted 40 minutes later; "a failed dev start means rebuild", when it never fails). There is no edit operation, so each correction is a delete plus a full re-send. That is the argument for `[[automations]]` over any timer: the engine re-derives conditions from row state every pass and has no prompt to rot. The uncomfortable half of the same report is that the manager **did not know the engine existed** while building precisely the thing it is for — a discoverability failure in wt's own bundled playbook, not a capability gap, and now named in the first section of `skills/manager/SKILL.md`. When a user of a feature reinvents it, the docs are the bug.
- **A fact that contradicts a field, but lives in prose beside it, does not exist.** A worktree wrote `BLOCKED ON A MOBILE RELEASE` into its own `ready --risk low` note; the fleet manager read the state, built a merge order, and told the human the branch was mergeable — twice — and the human caught it, not the fleet. Two independent readers, both with reason to look, both skipped the note. So the fix for "the vocabulary is missing a word" is rarely a longer note and is not automatically a new word either: `ready --blocked-on "<gate>"` is a FIELD (`blockedOn`, `isBlockedReady`) because "the work is done" and "it cannot land yet" are independent facts and a single state can only carry one — but the field only works because the RENDER changed with it (out of the merge band in `workRecordRank`, warn circle-slash instead of green, `blocked/ready` in `wt fleet`, `status.ready` automations suppressed). A field nobody's eye is drawn to is the note again. Note the scope discipline that keeps it sharp: it means exactly "do not merge yet", and post-merge ops (`apply this migration by hand`) stay in the note's `OPS:` line — admit those and the field degrades to "read the note", which is where this started. Three of the four fleet rows quoted as evidence were actually OPS, not gates — and the discriminator that survives contact is not "before vs after the merge" but **does merging make something WORSE than not merging**: a policy tightening whose migration is applied by hand is safe to MERGE and dangerous to FORGET (unapplied, nothing gets worse; the PR merely reads as shipped), which feels identical and is the case that will erode the field if admitted. And the field is only as good as the surface count: `blockedOn` reached `wt status --all --json`, `wt ls --json` and the TUI on the first pass but was silently dropped by `wt fleet --json`, which builds its `work` object field-by-field rather than spreading the record — so the MANAGER, whose primary sense that is, would have gone on reading `state: "ready"` off a gated branch. Caught only by querying all four against the fixture.
- **An equality test with a HAND-LISTED field set is a surface count in disguise, and this one drifted twice.** `setSlugWorkStatus`'s idempotent re-assert guard (same claim keeps the original `at`, so agents can re-assert without re-narrating in every watching TUI) compared `state`, `note`, `risk`, `sha` — written when those were all the fields there were. `blockedOn` and then `verifyAfterMerge` were both invisible to it, so amending ONLY a gate or ONLY the post-merge steps compared equal and the write was dropped. **What made it expensive is that the caller reported its own ARGUMENT back**: the CLI prints from the record it built in memory, so stdout confirmed a store that never happened, and the only way to find out was to read the row back, which nobody does after a tick. Three worktrees hit it and the fleet manager was asking worktrees to amend that field on the strength of the trailer. Two fixes, and the second is the one that generalizes: `sameWorkClaim` classifies fields through a total `Record<keyof WorkStatusRecord, boolean>`, so a new field cannot compile until someone decides whether it counts; and `setSlugWorkStatus` returns whether it WROTE, because a call that can legitimately succeed by doing nothing has to say which happened (the same lesson as `{ ok: true, adopted: true }`). When you add a field to a persisted record, the write path's comparison is a surface too — audit it alongside the JSON ones.
- **A record that dies with its row leaves two very different outcomes looking identical.** A worktree owing a `--verify-after-merge` check ran it, asserted `verified` with a detailed note, and was swept 2.5 minutes later — correct in every step. But `reapWtState` drops the per-slug record along with the worktree, so afterwards `wt status --all` had no row, `wt claude send` said only "archived on merge (#1359)", and nothing anywhere distinguished that from a row swept while the check was still owed. A fleet coordinator read the silence the second way and filed an issue to preserve a verification that had already happened — the cost is not the lost data, it is that the SAFE reading and the ALARMING one produce the same empty answer, so the reader has to guess and will guess wrong in whichever direction they fear. `RemovedWorktree.work` is now stamped by `recordRemovedWorktrees`, which reads it off the state it already holds under the lock rather than having callers thread it in — the writer holds the knowledge first-hand, and a removal path added later cannot forget. Note the read side is half the change and the easier half to miss: `parseWtState` whitelists fields on a removed entry, so a written-but-unparsed `work` would have round-tripped to nothing with every test still green. Absence stays UNKNOWN — `verification_owed: false` alongside `work_state: null` means the entry predates the field, never that nothing was owed.
- **A migration that rewrites `state.json` must re-stamp the writer sidecar.** `writeWtState` does it; `migrateAndPersist` reached `atomicWriteJson` directly and did not, so the v4→v5 bump moved the file's mtime while the sidecar still pointed at the pre-migration one — and the very next read fired `detectForeignWrite`, telling the user something that isn't this build had rewritten their state and may have dropped fields, plus "re-assert anything recorded recently". On the one occasion this build deliberately rewrote it and dropped nothing. Reproduced both ways in the fixture (with the stamp: one INFO line; without: the attention warning). It would have fired for every user on every version bump, and did on v3→v4 with nobody reporting it, because a one-time scary warning after an update reads as plausible. Any new path that writes the state file outside `writeWtState` carries the same obligation.
- **A field can change a state's RENDER in either direction, and the second direction is the one that needs guarding.** `blockedOn` pulls a `ready` row OUT of the merge band; `verifyAfterMerge` (a check only the deployed environment can prove) must pull it nowhere at all until the branch LANDS, because merging is the prerequisite rather than the thing gated — the moment it sinks a mergeable row it has become a second `blockedOn`, which is the failure it exists to avoid. What it does instead is survive the merge, and that is the whole feature: a landed row would otherwise take `LANDED_RANK`, wear the merge glyph, and become a `wt clean` candidate, so the check that can finally run is the one whose worktree just got swept, along with the only record that anything was owed. Hence the render inverts on landing (`owesPostMergeVerification` → sorts and reads as `needs-testing`, work dot instead of the merge glyph) and it joins `destroyHazards`, which is what makes every destroy path inherit the guard since sweeps never force. Two consequences worth keeping: the derivation happens at RENDER time, never as a write at merge, because no process is guaranteed to be running when a branch lands; and it is the one field a fresh assertion CARRIES rather than drops, because it describes the BRANCH rather than the assertion — a routine `wt status working` silently releasing the worktree back to the sweep would be a failure with no output anywhere. `verified` is its only discharge, and it is a real state rather than a flag because `dropped` means never landed and `ready` means still to merge.
- **Work status is asserted, never inferred-and-stored.** The eight-state vocabulary and its rules live in `core/work-status.ts`; the record is `WtSlugState.work`, written only by `wt status` (agents; validation lives in the CLI) and the `u` picker (human; deliberately lenient). Derived signals (session asking, merged/gone) fold in at RENDER/SORT time via `effectiveWorkState`/`rowWorkRank` — never write a derived state into the record. Attention-feed narration comes from diffing wtstate in `useWorkStatusEvents`, not from emit-at-call-site (the writer is usually another process). One field, two JSON paths: `wt fleet --json` nests it (`.work.by` — it joins three domains and must namespace them), `wt status --all --json` flattens it (`.by`). **Where a field's null is MEANINGFUL, a wrong-path query is indistinguishable from a correct answer** — `.work.by` against the flat surface returned null for all 12 rows, and "unattributed, failing open exactly as designed" was a fully coherent reading of that. It only came apart because `wt status <slug>` printed `via manager` and contradicted it. So: any doc naming such a field names its path and the other surface's, and a suspicious all-null column is worth one spot-check before it becomes a conclusion.
- **`wt ls --json`, `wt fleet --json` and `wt status --all --json` all append the same recently-removed history, so all three carry the same `kind` (`live` / `merged` / `removed`) — and a positive discriminator added to ONE sibling is worse than none.** `status --all` gained `kind: "live"` for the stated reason that a negative test "reads like a missing field rather than a deliberate one"; the other two kept absence, so the fleet had two conventions for the same question and each one silently returned the wrong set on the other command. A manager filtering `kind == "live"` on `wt ls --json` got zero rows, so it counted instead, cross-checked against `wt section ls` (live-only, legitimately 4 shorter), and concluded wt was failing to prune on remove. The general rule: **when you add a discriminator to one output surface, add it to every surface that shares the shape, in the same commit** — the half-migrated state is undetectable from either side, since each command looks internally consistent. Consumers then key on the VALUE, never on the key's absence: `remote-worktrees.ts` parses hosts running their own wt build, where `kind` has meant three different things, and a presence test there renders a populated host as an empty section.
- **`log.attention.*` is for "worth interrupting a scan", nothing else.** Status transitions, needs-you signals, escalations. Everything routine stays on `log.event.*` (the firehose); `event.err` already surfaces in the attention view by level, so don't double-emit errors.
- **Freshness is push-based; `r` is a backstop, not the mechanism.** Every external state source has an event trigger that invalidates the matching query — the full trigger inventory is in docs/architecture.md#freshness-model. When adding a state source or mutation path, wire a watcher or an explicit invalidation at the call site rather than shortening a staleTime or telling the user to press `r`; staleTimes only bound how wrong things can be when a trigger is missed.
- **Users update hot from main — every push is a release.** The safety net (docs/updates.md) only works if changes respect its contracts: (1) a shape change to `state.json` (WtState/WtSlugState) bumps `WT_STATE_VERSION` in `core/wtstate/migrations.ts` and adds a forward-only migration — never "just bust" the state file, it's the one non-rebuildable store; (2) persisted-query shape changes bump `CACHE_BUSTER` in `state/client.ts` (busting IS the policy there) — and so does a change of MEANING within an unchanged shape, since a restored entry is indistinguishable from a fresh one (`SyncState.remote` switching from `@{u}` to `origin/<branch>` at v13); (3) config renames get loader aliases + a deprecation warning, new fields get defaults or a copy-pasteable `Errors` message — a config that loaded yesterday must load today; (4) everything under `core/update/` and the `wt rollback` path stays config-free (no imports of config/proc/locks/logger at module load) so the crash-rollback offer works when the config loader itself is what broke; (5) keep `bun run typecheck` + `bun test` green on every push — CI green is what the update gate ships.
- **Pickers follow the shared modal UX rules** (trigger-key re-press confirms, Enter confirms, Esc/q/Ctrl+C cancel, 1–9 quick-pick, sub-affordances get their own letter). The full checklist is docs/architecture.md#modal-ux-rules — hold to it when adding or modifying any picker; deviations fragment the UX.

## Logging & debugging

- Daily app log: `~/.cache/wt/logs/app/wt-YYYY-MM-DD.log` — read it when something looked wrong; event lines are tagged `EVENT` (`grep ' EVENT '` shows what the activity pane showed). Destroy logs: `~/.cache/wt/logs/<slug>-*.log` via `wt logs <slug>`.
- Performance symptoms (machine slow, TUI laggy, runaway CPU/memory) go through the `/perf` skill (`.claude/skills/perf/`) — procedure plus a living notes.md with baseline, open issues, and known failure signatures. Update its notes when perf work teaches something.
- Adding a log call: `createLogger(source)` at module top (or per-call for dynamic slugs). `log.event.X` when the user should see it in the activity pane; `log.debug/info/warn/error` for file-only. `log.error` does **not** auto-promote to the pane.
- **Toasts vs. pane feeds — the contract.** The footer toast is a single latest-wins slot for "see this NOW"; the pane feeds are the record. Keystroke feedback (the flows' `ctx.toast(...)`) is toast-only and never logged — it acknowledges something the user just did. Background code never toasts directly: it rides the logger, where `log.attention.*` toasts by default (attention already means "worth interrupting a scan"; `{toast: false}` opts out) and `log.event.*` opts in with `{toast: true}` — reserved for async completions and failures whose trigger is long past (action finished, handoff sent, automation dispatched/failed, dep sync done). Consequence: every background toast has a pane line behind it, so a missed toast is always recoverable; and routine firehose chatter never toasts.

## Tooling

- Runtime is **Bun**. No node, no pnpm. `bun install`, `bun src/main.ts`.
- Typecheck: `bun run typecheck` (just `tsc --noEmit`).
- Tests are opt-in, not comprehensive: `bun test`. The restack anchor tests (`src/core/stack-ops.test.ts`) pin the squash-safe cut-point logic against real git repos — add cases there when touching `resolveAnchor`. Most other modules have no tests; smoke via the CLI.
- The TUI takes over the terminal — smoke-test refactors via the CLI subcommands (`bun src/main.ts ls`) or check imports with `bun -e 'import("./src/path.tsx")'`.
- **Validate and investigate TUI work with the probe harness, not by reasoning from source.** `scripts/tui-test.sh` drives a REAL wt instance in a throwaway tmux session: `start [name] [w] [h]` (defaults `probe 200x50`, waits for first paint, arms `WT_AUTOMATIONS=off` + `WT_GITHUB=off` so probes never dispatch automations or burn GitHub API quota — PR badges render from the persisted cache), `keys <name> <tmux keys…>`, `snap <name>` / `snap-color <name>` (capture-pane text / SGR colors), `stop <name>` when done. Any change or review touching layout, modals, keys, or colors gets snapshotted through it — at a couple of widths (e.g. 200×50 and 110×30) for layout work. It runs against the real config/state: navigation, pickers, and overlays are fine (Esc out), but never confirm destructive prompts (`d`, `c`, `Ctrl+R`), never press session-attach keys (`F10`/`F11`/`F12`, `;`, `,`, `.`, `m`, `/`) — those hand the probe's terminal to wt's private tmux server and the pane just looks hung — and never press keys that mutate real state without a confirm (`a` archive, `J`/`K` move row, `L` rename, `!` actions: a probe once archived a real row, and a stray `/` cold-started a live agent session). tmux eats a lone `;` (its command separator) — send `'\;'`. Concurrent probes are fine under distinct names. The read-only rules above apply to probes on the REAL config; a sealed second instance (exported `WT_CONFIG` + `WT_TMUX_SOCKET`, relocated `cache_db` — see docs/configuration.md "Running a second isolated instance") may exercise everything, including destructive flows and `WT_GITHUB=on`/`WT_AUTOMATIONS=on`.

## Traps

- **The fixture runs the DEFAULT backend, and the fleet may not.** `scripts/fixture.sh` writes no `[backend]` section, so it is `git-worktree`: every worktree shares the main clone's object database and therefore its refs. A live fleet on `rift` is the opposite — each worktree is an independent clone with its OWN remote-tracking refs, only as fresh as the last fetch inside it. Anything that resolves a ref with the worktree as cwd behaves differently in the two, and the fixture will confirm the version that is wrong for the user. Measured: `git rev-parse origin/staging` gave 10 distinct answers across 28 rows, one of them 9 merges behind, none the actual tip — while the same call in the fixture returned the current tip every time and a targeted test passed cleanly. That is how a base anchor for `examined` shipped resolving the *worktree's* stale view, reintroducing the exact missed-row failure the anchor was added to prevent. The rule: a ref that must mean "where the world is now" resolves in the MAIN CLONE (`baseTipSha`), which is where `fetchOrigin` fetches; a ref that must mean "what this checkout sees" resolves in the worktree. And when a comparison spans a write and a later read, both sides must use the same helper, or they are comparing reference frames rather than commits.

  **The general form, because backends are only one costume: an instrument that answers confidently about a world it is not in does not merely fail to catch the bug, it VOUCHES for it.** A green result is not uninformative — it is a positive claim that now has to be disproved before anyone looks again. Four instances in one day on this fleet, all wearing different clothes: a fixture on the wrong backend (above); a stale local database reporting 293 passing tests where a rebuilt one reported 327; a suite green on the machine's node 24 while CI pins 22; a SQL-only test that structurally cannot observe a gateway routing failure; and a probe run inside a container warm-up window, returning zero events on a correctly-configured subject. Before trusting a pass, ask which world the instrument was in and whether it is the one the claim is about — and note that every one of these was cheap to check and expensive to reproduce afterwards.
- **"Do I have the object" is not "is my ref current", and under `rift` the two come apart on their own.** The restack's trunk-root freshen gated on object PRESENCE (`hasCommit`), which reads true long before the ref moves: a plain `git fetch origin` inside a clone pulls GitHub's merge-queue branches (`gh-readonly-queue/<base>/pr-N-<sha>`), and a queue branch's tip IS the commit that becomes trunk minutes later. So the gate said "already fresh", `refs/remotes/origin/<trunk>` never moved, and the rebase landed on exactly the right commit while every later reader in that clone kept measuring against a tip several merges behind. The visible symptom is a lie in the safest-looking direction: a branch with NO commits of its own reported 3 ahead, because `origin/<trunk>..HEAD` counts the trunk commits between the stale ref and the tip HEAD was rebased onto. On a live fleet of 10 that hit 2 rows, one reporting 156 where the truth was 14 — and since an unpushed branch's `unpushed` count IS its ahead-of-base count, the destroy guards then refuse to remove an empty worktree, claiming work at risk. The rule is that a freshen gates on the ref's VALUE (`resolveNewBaseSha`), and anything COUNTING against trunk goes through `freshBaseRev`, which substitutes the main clone's sha when the checkout holds that object. Note that the wrong-frame count is invisible to review: both sides are ordinary git commands, both succeed, and the number is plausible.
  **But patching the readers was the wrong altitude, and finding the next reader is what shows why.** The counts were two surfaces; the same stale ref also feeds the pre-PR row title (the oldest commit in `base..HEAD`, which becomes a colleague's commit), the diff context the AI summary is generated from, the git row's files/insertions, and the conflict probe — which then reports clean against a trunk several merges old, a false green. Measured: a branch with NO commits of its own presented an 11-file, +482-line diff of someone else's work. And the reader that settles it can't be patched at all, because it isn't wt: the agent inside the checkout typing `git log origin/staging..HEAD`. `{{base}}` can't become a sha either — it is a ref NAME on purpose, since a base change kills the live diff session, and one that moved with trunk would kill it on every merge. So `fetchOrigin` now fast-forwards every worktree's own `origin/<trunk>` (`freshenWorktreeTrunkRefs`) and `freshBaseRev` is the floor beneath it. **And the floor was standing on sand: the trunk has TWO spellings and only one was normalized.** A fork-base record stores the bare name (`baseBranch: "staging"`); `effectiveBaseOrTrunk` matched `origin/staging` and fell through on `staging`, into its preference for a LOCAL branch of that name — which every rift clone has and which nothing ever moves, since the freshen touches `refs/remotes/origin/<trunk>`. `freshBaseRev` could not rescue it because it keys on the same trunk string, so it saw a non-trunk base and passed it straight through. Every ordinary trunk worktree therefore measured itself against clone time, permanently: 15 of 15 rows on a live fleet, local trunks 97 to 383 commits behind, one row claiming 383 ahead against a true 1. **The tell was nine different rows sharing one colleague's commit subject as their title** — a fleet-wide identical wrong answer is a resolution bug, never a data bug. Note how well the earlier partial fix hid it: busting `firstCommit` made the titles refetch, they came back identical, and the natural reading is "the fix did not land" rather than "a second cause produces the same symptom". **The floor also has to be applied reader by reader, and the title was missed for a day** — a row with 0 files and 0 lines changed titled itself "Make the pgTAP suite green and seed-independent", another worktree's commit, while the sync counts on the SAME row correctly said 0 ahead. Two readers of one question disagreeing is the tell, and the disagreement was that one went through `freshBaseRev` and one did not. Worse, `firstCommit` is persisted, so the wrong title outlived the ref fix and needed a `CACHE_BUSTER` bump to clear: a restored entry is indistinguishable from a fresh one, which is the same rule that governs a change of MEANING inside an unchanged shape. Cheap because of WHICH comparison leads: the ref-value check exits first for every git-worktree checkout and every current clone, and the object is nearly always already present, so it is a ref write rather than a transfer (~75ms for 18 checkouts against a 1.6-2.3s network fetch; 0 of 19 needed the fallback). Fast-forward only — a clone fetches for itself too, and rewinding its ref is the same lie pointing the other way.
- **A shape the real board can't show is a fixture away, not an argument.** `scripts/fixture.sh` builds a SEALED instance (own config, own cache root, own `WT_TMUX_SOCKET`, throwaway repo under `$TMPDIR`) whose board carries every shape the renderer branches on — a co-located chain, a fan, a split stack, one row per work status, a dirty row, a commit-less row, a landed pair (clean + dirty) that is the `c` sweep's candidate set: `build`, `probe [name] [w] [h]` (build if needed + start a TUI probe), `wt <args…>` (any wt command against it), `rm`. It drives the working tree's code through public CLI commands only, so it breaks loudly rather than drifting. Reach for it whenever a rendering question can't be answered from the live board — conditional affordances render nothing when their input is absent, which is indistinguishable from broken, and three of four "regressions" reported in one morning were absent inputs. Being sealed, it may exercise anything the read-only rules forbid above. It also configures a real `[dev_server]` on ports 8700+, so `wt dev` and the browser-tab cleanup keyed to the port are exercisable for real. It can't fabricate PR/check/merge-queue badges (they need GitHub), fold state (press Tab), or a stale status (needs age).
- **A guard that needs a record fails OPEN on every row that has no record.** `branchIsMerged`'s vacuous-containment check ("a branch with no commits of its own is not started, never merged") measures against the wtstate fork-base anchor, and `wt new` only wrote one for `--base` forks — so it was inert for every ordinary worktree, which is most of them, and `merged` both closes GitHub issues and feeds the clean sweep. Its only backstop was the first-parent SHA set, a module-level cache five of `fetchOrigin`'s six callers forgot to invalidate. Two independent fail-open paths, same blast radius. When adding a safety check keyed on stored state, ask what it does when the state is missing, and count the population that's in — here it was 12 of 13 rows.
- **"Safe to clean" and "safe to delete" are different questions, and no backend answers the second for you.** `isCleanCandidate` is a claim about the BRANCH (it landed upstream); whether the checkout still holds uncommitted work is independent, and a merged worktree collects new edits the moment anyone reopens a session in it. `d` had the dirty/unpushed guard; the `c` sweep and `wt clean` did not, and passed `force: false` to a backend on the assumption it would refuse — `git worktree remove` does, `rift remove` does not (its `--force` is advisory). Under rift that cost 16 uncommitted files in a merged worktree, unrecoverably: an independent clone's objects, branch and reflog go with the directory, so there is nothing dangling to fsck. The guard is `destroyHazard` in `tui/app-helpers.ts` (shared by `doRemove`, `doCleanRows` and the confirm modal, so the modal's count can't promise a row the sweep will keep) plus the `worktreeIsDirty` filters in `cli/commands/{rm,clean}.ts`. Its "still loading is a hazard, not an absence of one" branch is the load-bearing part. Any new path that removes a checkout consults it; sweeps never force, because forcing is a per-worktree decision.
- **"Unpushed" means "not on `origin/<branch>`" — never anything `@{u}`-derived.** wt points a worktree branch's upstream at its BASE, so every `@{u}` count answers "ahead of base", and both destroy guards were reading it as "would be lost": a fully pushed branch with an open PR refused `wt rm` and got kept by the `c` sweep, telling the human work was at risk when none was. `SyncState.remote` now measures against the branch's own remote ref (which also makes the row's `(…)` group stop duplicating `[…]`, and its help-legend entry true), `pushCounts().unpushed` is the CLI answer, and `localOnlyCommits` in `app-helpers.ts` is the one derivation both TUI paths use. Its fallback carries the other half: with no `origin/<branch>` at all, commits since the base are local-only work UNLESS the branch landed, where the same commits are a squash merge's pre-squash originals. A guard that cries wolf gets forced past by reflex, which costs more than the guard ever saved.
- **`BUN_INSPECT` is inherited by every bun descendant, so opening a session's message socket is not a private act.** wt launches each Claude session under `BUN_INSPECT=ws+unix://…/insp/<tmux name>.sock` (the transport in `core/harness/claude/inject/`), and bun honors that variable in every child, which then fails to bind a socket its own parent owns. **What that costs is not uniform and the worst case is silent**, so never read the EADDRINUSE stack as cosmetic: measured on bun 1.3.14, `bun test` and a trivial script never try and exit 0, a script touching the `Bun` global prints the stack and exits 1 with its body unrun, and `supabase functions deploy` (the CLI is a bun-compiled binary) prints the same stack and exits 1 **having deployed nothing**. An agent that trusts the output ships nothing and reports success. (On Linux the upstream fleet saw the child WIN the socket and orphan the parent's.) Hence `bin/wt` re-execs under `env -u BUN_INSPECT`, and `inject/shims.ts` puts a scrubbing shim on each session's PATH for every bun-compiled executable it finds there. **The harness binaries are deliberately NOT shimmed** (`NEVER_SHIM`): `claude` is itself bun-compiled, and the session launches as bare `claude` through that same PATH, so a shim would strip the variable from the session wt just set it for — silently costing every session its transport, which is exactly how it was found (a live send failing with "no inspector socket").
- **A shim on PATH is only as good as PATH being consulted, and `pnpm exec` / `npx` do not consult it.** They prepend `node_modules/.bin` and resolve there, so a shimmed `supabase` is bypassed and the unshimmed one runs with `BUN_INSPECT` inherited — dying EADDRINUSE on the *session's own* socket. Note where the diagnosis goes wrong: the socket is named for the tmux session (`insp/wt.sock`), the holder is that session's own claude process, and the dev server has nothing to do with it, so the failure reproduces with zero dev servers running and reads as a broken database stack rather than an env collision. That also rules out "stop exporting it to the shell": `BUN_INSPECT` IS the transport, and the session is the process that must have it. The fix is the `LAUNCHER_SHIM` floor — shim the launchers themselves, which discovery can never find (they are node scripts, no `__BUN` segment) and which covers every binary they will ever resolve. Their PATH entries are fnm per-shell dirs, so each shim re-resolves on PATH when its baked path is gone, dropping BOTH the generated dir and its own `$0` dirname: dropping only the generated one let a copy elsewhere re-find itself and exec forever, and the test that guards it is spawn-bounded, since a hang is not a test result.
- **The remaining hole in the shim is an ABSOLUTE PATH, and house style walks straight into it.** Every layer of the `BUN_INSPECT` defence is PATH-shaped: discovery shims what is on PATH, the `LAUNCHER_SHIM` floor covers what `pnpm exec`/`npx` resolve, and `pathWithShims()` puts the generated dir first. None of it is consulted by `/opt/homebrew/bin/supabase`. That is not a hypothetical: the standing guidance that shell aliases do not exist inside `.sh` files, so a script should call the full path to the underlying tool, is correct about aliases and is exactly the wrong move for a shimmed binary — an agent following it writes the absolute path into a script and re-creates the failure with every shim present and correct. Measured against a bound socket: the absolute path exits 1 with **zero bytes of stdout** and a 2.6KB bun stack, the shimmed name exits 0 with 3.9KB of help. A tool that prints nothing for `--help` reads as a broken install, so the search starts at PATH and installs rather than at the environment. Diagnosing it is cheap ONCE you suspect it: `ps -E -p <session pid>` shows both `BUN_INSPECT` and whether the shim dir leads PATH, which settles configured-correctly-but-bypassed in one command. So the rule for anything bun-compiled inside a session is to call it by NAME and let PATH find the shim, and reserve absolute paths for the alias problem they were written for.
- **A list of names only ever covers what someone remembered, and here the gap is silent.** The shim set was hand-written, and it was wrong in both directions within a day: `claude` was in it and must never be (above), `supabase` was not and had to be. So `ensureInspectShims` reads the machine instead — every executable on PATH over 8MB whose Mach-O header names a `__BUN` segment, which is what `bun build --compile` appends (4 of 1866 PATH entries here, ~30ms, header-only because the binaries run to 292MB). The exclusion is the dangerous half and is the one thing still written down, so `shims.test.ts` cross-checks `NEVER_SHIM` against the harness registry: a future harness whose binary is bun-compiled would otherwise walk into the trap with nothing to notice. Discovery is Mach-O-specific, so `ALWAYS_SHIM` keeps `bun` as a floor where it finds nothing.
- **A generated directory that PATH resolves is a SET, and code that only ever writes treats it as a floor.** `inject/shims.ts` computes what to shim; `ensureInspectShims` wrote each entry and pruned nothing, so removing `claude` from the list in `4eda658` — a fix for the exact trap above — left the file on disk, where PATH kept finding it. Every session wt launched for the next day had `BUN_INSPECT` stripped by the shim wt had just set it for: zero sockets ever bound, 374 typed fallbacks, and `wt doctor` reporting "6 of 6" as six independent per-session problems. **A source fix cannot heal state a broken version already wrote**; only a reconciling pass can, so anything generated into a directory gets pruned to the set that should be there, not merely written. The diagnostics carry the other half: `staleShims()` runs before either one blames a session's age, because when one cause explains 100% of a population it is not a per-instance cause, and the remedy they were giving (restart the session) was the one thing guaranteed not to work.
- **`Socket.write` is not all-or-nothing — it returns how much it took, and the rest is yours.** Measured on a unix socket with the peer busy in JS: 4500 bytes go whole, 5000 writes 2692, 8000+ returns 0. The inspector client ignored the return value, so every websocket frame past ~4.5KB was truncated mid-payload; the peer waited forever for the rest, and the send surfaced as "did not acknowledge the submit". Because the threshold is a function of SIZE alone it read like an escaping bug, and the hunt went through the payload for bad characters instead. Any new socket write buffers the remainder and resumes on `drain`, and queues strictly FIFO — a frame written into the middle of another one's payload corrupts the stream for every message after it, which is worse than the truncation. Note the test trap: a stub that reads eagerly accepts 5000 bytes fine, so a regression test at the field-observed size passes with the bug reintroduced and guards nothing (`client.test.ts` uses 200_000).
- **Every cheap readiness signal a component offers is about the component, not about being useful.** `wt dev start` exits 0 (launched), the port listens (serving), Postgres accepts connections (up) — and none of the three mean the migrations applied. A dev command that runs `supabase start` and THEN `migration up` fails its second phase in the background, minutes after wt reported success, leaving a serviceable stack on a stale schema behind a green tick and a working URL. It cost a day: a worktree reported a 305-test suite as red because every migration-dependent test asserted against a half-migrated database, a second worktree was spun up to fix the non-problem, and the `origin/staging` comparison run to confirm it was invalid too — it varied the code while holding the broken database fixed. The failure presents as a defect in the repo, so the investigation goes the wrong way from step one. Hence `[dev_server] health_command` (the project answers, because wt has no idea what a migration ledger is) and `--wait` meaning "usable", not "slot acquired". **The second-order trap is worse and caught the fleet's own workaround**: a check that runs ONCE cannot tell "not yet" from "wrong" — a replay in progress reads 29 of 35 applied, identical to a stale volume stuck at 29, and it settled at 35 a minute later. So the quiescence wait lives in `waitForDevReady`, which re-runs the check rather than believing one answer, and `wt dev status` reports an unhealthy young server as possibly-unfinished startup instead of sending someone to rebuild. Same shape elsewhere: realtime delivers nothing for ~a minute after start while the replication slot builds, so a probe in that window returns zero events on a correctly-published table. Anything that says "ready" is a claim about a lifecycle, and the only question that matters is whether the thing does its job yet.
- **`start` is also `restart`, and that is right for a RUNNING server and destructive for a STARTING one.** `startDevServer` killed the session unconditionally, so a second start against a supervisor still booting tore it down mid-flight. The sequence was wt's own advice: `wt dev reset` ends by launching and returns 0, and the launched-banner said to run `wt dev start --wait` to wait for it — which killed that launch, against an environment whose state the reset had just dropped. Two worktrees hit it independently and both arrived at the same byte-identical remedy, which is the strongest signal either report carried. **The residue is the expensive half and it is silent**: a half-initialised database volume survives the kill, so the next start finds an existing database, takes its reuse path, and never re-provisions what only a FRESH initialisation creates — 0 of 22 storage buckets while the migration ledger reads fully-migrated, because the migrations really did apply. It surfaced as unrelated pgTAP suites failing bucket assertions, which reads as "my change broke storage". Note that the intermittency is explained by the same mechanism rather than arguing against it: a kill after the database is up leaves a complete volume and costs nothing, so only a kill DURING initialisation is destructive. The fix is adoption (`{ adopted: true }`, the same shape as the harness-session race) keyed on `starting` — restarting a running server and recycling a parked one both stay as they were. **And the reported mechanism was a "race" both times; it was not.** The kill was unconditional, so the outcome was deterministic and only the TIMING of the kill varied — which is why "add a sleep" or "poll first" would have looked like it worked.
- **A recovery path that treats "already exists" as success makes its own failure unrecoverable.** `startHarnessSessionDetached` returns ok when `tmux new-session` fails but a session of that name is present — written for a genuine race with a concurrent creator, and correct for it. But tmux refuses duplicate names, so the same branch also swallows "a session by this name exists and is broken": the start creates nothing, waits out the 20s registration timeout, and reports `Claude started but did not register`, which reads as a timing problem. The retry re-adopts the same corpse and fails identically — two attempts 42 seconds apart are in the log for `edge-fn-io-timeouts-compensation`, and three for `meetings-dead-code`. Only `wt claude stop` cleared it, which nothing told the reader. The fix is that the two cases must be DISTINGUISHABLE at the boundary (`{ ok: true, adopted: true }`) and diverge afterwards: an adopted session that misses the full timeout is recycled once (safe precisely there — lock held, nothing registered, the race has had its entire window), while a session we created and that failed is not, because recreating it reproduces the failure. General shape: when a call can succeed by doing nothing, its result has to say which happened, or every caller downstream inherits an ambiguity it cannot resolve. The diagnostic half matters as much — a start failure now quotes the pane, since the wrapper's `.err` file is empty in every observed instance and `wt logs <slug>` answers about destroy logs, so there was nowhere at all to see why.
- **A tmux session's environment comes from the SERVER's birth environment, not from the client that ran `new-session`.** Verified: with a server already up, `FOO=second tmux new-session …` gives the new session `FOO=first` — whatever the process that started the server had. So "my own env already has X, nothing to do" is never a safe inference about what a session wt is creating will see, and only an explicit `env VAR=… cmd` prefix (which `wrapInnerArgs` builds) reliably wins. This is why `pathWithShims()` always emits a full PATH instead of skipping when the shim dir is already present: the skip silently un-shimmed exactly the nested case — wt run by an agent, creating another session — that it existed for.
- **wt usually runs inside a Claude session, so wt's environment is a Claude session's environment.** Anything wt forwards to a session it spawns is inherited from whoever ran wt — and `CLAUDE_CODE_CHILD_SESSION` makes the new session treat itself as a child and **stop writing a transcript**, which is what wt reads for delivery confirmation, status, summaries and the away feed. Started from a shell it looked perfect; started by an agent (i.e. almost always) it silently lost all of it. `wrapInnerArgs` unsets it. Any new "pass the environment through" path asks the same question: whose environment is this, really? The corollary bit twice more: **a stamp that is only ever ADDED is inherited on every branch that doesn't add it.** `WT_AGENT` and `BROWSER_CONTROL_SESSION` are deliberately withheld from some sessions (a human's `F10` shell must not send mail signed as that worktree's agent; a slug-less session owns no browser tabs), and withholding them did nothing at all — the caller's values were already there. Both are now in `wrapInnerArgs`'s unset list, added back only where earned. Note where this hides: `bun test` from a session sees the ambient values, CI does not, so the suite is GREENER in CI than on the machine. Run it inside a session before believing it.
- **The prompt injector's anchors belong to Claude Code, not to us.** `inject/page-routine.ts` walks a live React fiber tree by structural props (`onSubmit` + `messagesRef`/`commands`, `value` + `onChange`). That survives minifier churn but not a restructuring, and a Claude Code update is what would do it. Keep the routine an opaque string ported from upstream rather than idiomatic TypeScript, re-derive it against a live session when it breaks, and never make a change there that `wt claude selftest` (also the `messaging` banner in `wt doctor`) can't confirm.
- **The list panel (`src/tui/panels/list.tsx`) is NOT row-driven.** Different layout (single line of glyphs, no labels), intentionally not wired through `rows/`. Don't try to unify them.
- **Config loads once at module init.** No hot reload — editing the TOML requires restarting `wt`.
- **Remote argv never crosses SSH as raw arguments.** OpenSSH reparses its command through the remote login shell (Fish on the first supported host). Route commands through `core/remote-protocol.ts` + the `_remote` entrypoint; do not interpolate user input into the SSH command string.
- **`Bun.TOML.parse` is built in.** No external TOML lib needed; don't add one.
- **Never park a process on a bare `await new Promise(() => {})`.** With no other pending handle, Bun spins the event loop at 100% CPU instead of blocking (bun 1.3.14; cost a 19h CPU-time burn in a long-lived pane entrypoint). A long-lived idle process needs a real handle to block on — an inert `setInterval`, or `process.stdin.resume()`. Applies to any new `_`-prefixed entrypoint that's meant to just sit there.
- **Never animate through OpenTUI's Timeline engine (`useTimeline`) or `requestAnimationFrame`.** Any playing timeline holds a renderer-wide "live" request: the render loop goes continuous (full tree walk + full repaint per frame, `requestRender()` becomes a no-op so keypresses can't pull a frame forward), and it stays that way until every timeline stops. Two forever-looping timelines in the header wave once kept the app in that mode from boot to quit — ~13% CPU at rest and a standing input-latency tax. Chrome animation goes through the shared ticker in `tui/spinner.tsx` (`useAnimationTick`), which is refcounted and drops to zero frames when nothing animates.
- **A timeout on our own event loop is not evidence about the outside world.** libuv runs the timers phase before the poll phase, so a loop blocked past a deadline fires the timeout callback *ahead of* an IO event that already landed. The dev-server port probe raced a 400ms `socket.setTimeout` against `connect` and reported "nothing is listening" for a live server whenever the TUI stalled (reproduced at 500ms; a 574ms block is in the logs) — the bolt dropped off the row and `s` refused to open a working URL. Any probe of this shape is three-valued: the definitive negative (here `ECONNREFUSED` — on loopback a dead port refuses instantly) means "no", and a timeout means `unknown`, which must never collapse into "no". See `probePort` in `core/dev-server.ts`.
  **The same lesson with no event loop in it: a SIGKILLed command's empty stdout is not an empty world.** `run()`'s `timeoutMs` kills the child and returns what was captured, and a command that BUFFERS (lsof does) has captured nothing — so a blown budget yields zero bytes and exit 137, which parses to an empty list indistinguishable from a completed scan of a machine with nothing listening. The destroy reaper read it that way, so under load it silently skipped its reap, leaving a dev server holding the port block that the next worktree then failed to bind — the failure surfaces much later as a bind error naming nothing wt knows. The margin makes it look impossible right up until it isn't: the scan is 76ms on an idle box against an 8000ms budget, a 100x cushion, and a fleet saturating the machine still closed it (the observed test failure is at 8028ms, which is the budget, not the code). `RunResult.timedOut` now carries the distinction and `lsofScan` treats two blown budgets as UNKNOWN, retrying once and then narrating on `log.attention.*`. Any new caller that reads a command's output as an answer about the world checks the flag.
- **wt supervises a PROCESS, and on any modern project that is not where the load is.** `pnpm dev` used to be vite; cozee's now runs `supabase start`, which hands twelve containers to the docker daemon and *returns* — so killing the tmux session takes vite down and leaves the stack up, indefinitely. Measured while `[dev_server] max_concurrent` was being designed: four Supabase stacks running, exactly one with a live dev session, two of the survivors nineteen hours old. Note what that does to the obvious fix. "Cap concurrent dev servers" was the request, and a cap on dev *sessions* would have counted 2 while the machine carried 4 — governing a number with no relationship to the load, which is worse than no cap, because it reads as solved. So the cap ships with `[dev_server] stop_command` (`core/teardown.ts`, shared with `[lifecycle] destroy_command`), and the rule generalizes: before rationing something, check that the thing you can count is the thing that costs. The two hooks stay separate keys — a destroy teardown may drop volumes, and running that on an ordinary `wt dev stop` would be a nasty surprise.
- **A coordination decision that must be acted on by an agent loses to any event that happens instantly.** Getting an urgent worktree to the front of a full dev-slot queue took four messages and still came out wrong: the manager asked a holder to release and asked the queue leader to stand aside, the holder released, and the freed slot went to the leader anyway — a slot promotion is instant, a message to an agent is not, and the two crossed. Three agents cooperated correctly and the ordering was still wrong, which is the tell that the protocol was social where it needed to be written down. So `wt dev queue <slug> --first` edits the WAITER'S OWN entry: the promoted agent does nothing, its next poll re-reads the queue and finds itself at the front, and there is no window to lose. Note the two shapes that fell out of the existing principles rather than being designed: a TIER, not an index (an index is a total order needing renumbering on every join, departure and pruned-dead waiter, while the thing anyone wants to say is "this one goes first"), and it lives in the self-expiring waiter file, so a promotion covers exactly the current wait. The self-promotion refusal is the same ownership rule as everywhere else — relative urgency across a fleet is unknowable from inside one worktree, and a tier anyone can claim for themselves is a tier everyone claims.
- **A teardown that may fail is fine to ignore before a DELETE and not before a DISCARD.** `runTeardownCommand` logs a non-zero `stop_command` and carries on, which is right for `destroy_command` (refusing to delete a worktree because its teardown script broke is a bigger leak than the one it fixes) and was wrong for `wt dev reset`, whose next step drops the environment's state. Discarding volumes underneath an environment that is still up leaves it unstartable in a way that reads as a broken TREE: the reporter had just re-stamped three migrations, and the project's own issue tracker had "a re-stamped migration crash-loops the dev server", so the first suspect was their diff. Two things worth separating here, because the first guess was wrong and would have sent the fix to the wrong place: the ORDER is already correct (`resetDevServer` runs `stopDevServer`, hence `stop_command`, before `reset_command` — proved with timestamped hooks in the fixture), and what actually bites is that wt supervises a PROCESS while the state lives in something else, so a failed `stop_command` is the ONLY signal it has that the environment is still there. Hence `runTeardownCommand` returns whether it took, and `resetDevServer` throws `DevResetStopFailedError` rather than discarding. Note which way it fails: nothing is touched and the environment is whatever it was, because for a discard the safe direction is refusing.
- **A `stop_command` built out of raw container commands tears down the containers and not the TOOL's idea of them.** cozee's is `docker rm -f` by label, which is correct about the containers and leaves the Supabase CLI believing the project is still running — the next `supabase start` answers "already running" and the database container never becomes ready, cleared only by that CLI's own `supabase stop`. The general rule for the hook: prefer the project's own teardown over the container commands it happens to issue, because anything that starts a stack usually keeps state about that stack, and removing its containers behind its back is not the same as stopping it.
- **A sweep is blind in the shape of its finder, and wt has two whose blind spots line up.** The destroy reaper matches processes holding a listening socket with a cwd inside the worktree; the port allocator probes the one port it hands out. A docker container defeats both at once: it has no cwd in the worktree and its host ports belong to the daemon, so the reaper never sees it — and the port that then collides is not wt's. cozee's stack occupies a ten-port block that is NOT a function of the dev port wt allocates and is not derived in the `[dev_server] command` at all — `{{port}}` varies only vite's, and the block comes from the repo's own registry (measured live: dev ports 8101/8103/8104/8106 map to kong 55341/55321/55351/55371, in no order). So the two numbering schemes are independent, and a destroyed worktree's containers kept 55330-55339 while wt correctly probed 8100, found it genuinely free, and reassigned it; the next worktree died three times on `Bind for 0.0.0.0:55332 failed`, naming nothing wt knows. **Note what that rules out: "make allocation check reality" was the obvious fix and was already implemented** (`portInUse` treats a `probePort` `unknown` as taken) — a probe aimed at the wrong port is not a missing probe, and no amount of hardening it would have helped. The fix has to live where the knowledge does, so it's `[lifecycle] destroy_command` (`core/lifecycle.ts`), a project-supplied teardown that generalizes past docker to tunnels and sandboxes. It never blocks a destroy: refusing to delete a worktree because its teardown script broke is a bigger leak than the one it fixes.
- **A slug is routinely a strict prefix of another slug, so matching one by prefix or substring silently selects a neighbour.** Worktrees derived from the same issue lead with the same id, so `coz-1691` and `coz-1691-domestic-bovid` coexist by design, and `-` (the separator every such pair splits on) is legal *inside* a slug — which is exactly what makes `startsWith(\`${slug}-\`)` unsafe where `startsWith(\`${slug}~\`)` is fine (`~` can't occur in a slug; see `harness/claude/harness.ts`). Two live instances: the `destroy_command` example in docs/configuration.md shipped an UNANCHORED `docker --filter name={{slug}}`, whose name filter is a regex, so destroying `coz-1691` would have torn down `coz-1691-domestic-bovid`'s running stack (measured: 12 containers matched, all the other worktree's; `_coz-1691$` matched 0). And `latestLogFor` picked the newest file by `startsWith`, so `wt logs <slug>` could tail a longer-slugged neighbour's destroy log with nothing to signal it. Both now match EXACTLY — the log path via `destroyLogSlug`, shared with `reapDestroyLogs` so the two can't drift apart on what a slug's log is. **And anchoring the name was itself the wrong fix, which took a day to surface**: the Supabase CLI truncates its project id to 40 characters, so for a 41-character slug (`meetings-notifies-before-actually-joining`, live on this board) `--filter name=_{{slug}}$` matches *zero* of the 12 running containers. A teardown that quietly does nothing is indistinguishable from a teardown with nothing to do, which is worse than the over-match it replaced. The answer is to stop reconstructing the name at all and match an identity the tool stamps on what it created — `--filter label=com.supabase.cli.project=$(printf %.40s {{slug}})`, an equality test with no anchoring question and no prefix collision. `com.supabase.cli.workdir` carries the full untruncated path and would also work — it is on the database container too, contrary to what this bullet claimed until the labels were re-read on a live stack; the `project` filter stands on its own merits (an equality test on the id the CLI actually keys its compose project by), not on that. Count the matches before believing a filter, and re-read a label before believing a note about one.
- **A test that calls `run()` passes an explicit `cwd`, and the suite is where that bites.** `run()` defaults cwd to `config.paths.mainClone`; CI's config names `/tmp/wt-ci-fake-main` and never creates it, and `Bun.spawn` fails on a bad cwd BEFORE reaching the binary — so the call returns `{stdout: "", exitCode: -1}` in under a millisecond, which looks like the command answering rather than never running. Green locally, red in CI, twice in one day (`010c583`, then three `run timedOut` tests). The asymmetry is what makes it easy to walk into: `runStreaming` sits in the same file and leaves cwd undefined, inheriting the process's, so the tests directly above yours are fine without it. Reproduce before pushing by copying CI's config block out of `.github/workflows/ci.yml` and running `WT_CONFIG=<copy> bun test` — the local config's `main_clone` exists, which is exactly why the local run vouches for it.
- **macOS-only utilities** (`open`, `pbcopy`, `osascript`, launchd) are assumed. Anything that shells out to them stays guarded by the macOS assumption noted in the README.
- **AppleScript can't take a variable application name.** `tell application X` is resolved at COMPILE time, so a script naming an app that isn't installed fails entirely (a `try` around it doesn't help — compilation precedes execution), and `tell application someVar` won't load the app's terminology, so `tabs`/`URL` come back as syntax errors. The pattern that works is in `core/browser.ts`: filter to RUNNING apps by process name first, then generate one script per app with its name baked in as a literal.
