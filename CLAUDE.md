# wt — for Claude

Personal git-worktree TUI. Single developer, single machine, OSS-published. Bun + React + OpenTUI on top of TanStack Query.

## Workflow

Commit and push directly to `main`. Don't create feature branches, don't open PRs, don't suggest either — unless the user explicitly asks. This is a single-developer repo and the feature-branch dance is pure overhead here. When in doubt, stay on `main`.

## Architecture (rules; map in docs/architecture.md)

- Three layers — sources (`src/state/queries/`), rows (`src/tui/rows/`), driver (`src/tui/panels/details.tsx`). Rows are pure-presentational; fetching stays in sources. Don't cross the boundaries.
- `src/tui/app.tsx` is the composition root and only routes; new flow logic goes in `src/tui/flows/`, new modal keys in `src/tui/modal-keys/`, not back into app.tsx. Keyboard dispatch order (modal → footer input → removed view → `h` → normal) and the handler order inside `normal-keys.ts` are load-bearing.
- Big core modules are directories behind same-named flat barrels (`core/github.ts` → `core/github/`, …); only names re-exported by the barrel are public, and importers use the flat path. Per-harness code lives under `core/harness/<harness>/` behind the `Harness` interface.
- `src/core/config.ts` defines the config contract (fail-fast loader, optional sections `null` when absent, `requireSst()` for SST-only paths). Read the stable-files list in docs/architecture.md before touching contract files.
- **A CLI command imports only what it needs — `cli/index.ts` is a map of lazy `() => import(...)` loaders, never static imports.** Users update hot from main, so any push can put a broken module in front of every agent on the machine; static command imports meant one bad export took out all 21 subcommands at once, including the `wt status` an agent uses to say it's stuck. The same rule applies *inside* a command whose branches have different needs: `wt manager report` writes a spool file and imports no session machinery, precisely so the fleet can still report that delivery broke. Not importing statically costs nothing — tsconfig has no `include`, so `tsc --noEmit` type-checks every module regardless of who imports it. Verify with `scripts/broken-module-check.sh`, which breaks a leaf module in a throwaway copy and prints which commands survive.

## Working principles

- **Only encode facts that are write-once and self-expiring.** A field that needs upkeep will drift, and a drifted field is worse than prose — prose is visibly dated, a field looks authoritative. Corollaries: bundle new state onto an existing mandatory step rather than minting a command or prefix ritual (rituals get forgotten — the `wt run --managed` rejection); close the hole in the tool over teaching agents a habit (the destroy reaper, `gh-merge-base` at create); assign ownership to whoever holds the knowledge first-hand, never to the relay; absence of a value means "unknown", never "fine". Worked rejection: a fleet-level decision queue — nothing would close its items automatically, so it would rot into a hand-maintained list; the `ready` notes already carry that information. Worked acceptance: merge edges (`core/merge-edges.ts`) — pairwise assertions that decay the moment either branch moves.
- **Offload the human, always.** wt exists to shrink human involvement to the parts only a human can do — merges, logins/credentials, judgment calls, risk acceptance. Everything agents are good at, and everything deterministic code can do, moves to agents or into wt itself. This is top of mind for EVERY changeset: when building, apply it automatically (don't add a manual step where a watcher, an automation, a status assertion, or a manager briefing could absorb it); when designing, actively propose moving existing human work to agents or code. The intent doc is docs/fleet.md — read it before status/manager/automation-shaped work, and update it in the same commit when a change moves the human/agent boundary.
- **Source fetches stay batched.** The github source is one GraphQL round-trip aliasing every per-worktree PR field plus the repo `mergeQueue` block. Never split it into per-row fetches; rate limits and latency are real. New PR fields go into `PR_FRAGMENT` in `core/github/fetch.ts` rather than getting their own query.
- **AI summary is hash-keyed.** `aiSummaryQuery`'s queryKey is `["aiSummary", <hash>]`; equivalent diffs across rebases/amends/renames hit the same entry. "Previous summary stays visible while a new hash fetches" comes from `placeholderData: keepPreviousData` at the observer — no mismatch effect, no force-regen flag; the hash flipping IS the trigger. `refreshAiSummary` (`t`) refetches the diff context and `removeQueries` the entry for the resulting hash.
- **Pluginify reactively.** Built-ins now, plugins only when there's a second concrete implementation that justifies the seam. Don't pre-design for "what if someone wants Jira."
- **No client-app defaults in code.** `paths.main_clone`, `paths.worktree_root`, `branch.prefix` are required and the loader refuses to start without them. New required fields go through `Errors.reqStr`; add a derivation when one's natural (see `stage.prefix` defaulting from `branch.prefix`).
- **Errors render verbatim, gated on retries-exhausted.** `firstError` in `details.tsx` already handles the gate (`error && !isFetching`) — don't duplicate it elsewhere. The same error showing on every row that depends on a broken source is intentional.
- **Convention over configuration for the niche stuff.** `branch.id_pattern` exists but most users will never set it; the default matches Linear/Jira/Shortcut conventions.
- **Stacks are inferred, never stored.** The per-slug fork-base record (`baseBranch` + `baseSha` in wtstate) is the ONLY stack state; grouping, diff bases, and the restack engine all derive from it (`core/stack-layout.ts` infers, `core/stack-ops/` replays). Don't add stack registries, manifests, or membership caches — and never drop a `baseSha` when rewriting a record's branch: it's the squash-safe replay anchor (see docs/stacked-prs.md). The record is written for **trunk** forks too, even though they're stacked on nothing — every reader normalizes `baseBranch == trunk` to "no parent", and the anchor's second consumer is `forkBaseIsVacuous`, which needs it to tell an unstarted branch from a landed one.
- **"Merged" is a claim about work, not about reachability.** `branchIsMerged` gates containment on the branch having commits of its own since its recorded fork base (`baseSha`), because "every commit is on trunk" is vacuously true for a branch that added none — and that population is precisely every stacked worktree between `wt new` and its first commit. Left ungated it cost two GitHub issues, closed autonomously, describing work nobody had started. Any new predicate that means "this landed" carries the same guard, and anything that writes OUTSIDE wt off the back of one (`builtin:close-issue`) narrates on `log.attention.*`, since wt's undo doesn't reach there and the board shows nothing.
- **Mutating GitHub state? Invalidate `["github"]`, not the worktree.** Write-path `gh` calls must trigger `refreshGithub()` from `state/hooks.ts`. `invalidateWorktree(slug)` looks plausible but the github query is keyed by branch list, not slug — it silently misses.
- **Automations are level + ledger, never edge-triggered.** The `[[automations]]` engine (`core/automations.ts` ledger, `tui/automation-rules.ts` pure evaluation, `tui/hooks/useAutomations.ts` queue + dispatch) re-derives conditions from row state every pass; once-only comes from persistent fire keys keyed on head SHA. Hard rules: `markFiresDispatched` runs synchronously before any await in a dispatch; PR-driven conditions require `githubFresh` plus `pr.headRefOid` (persisted-cache data must never fire); failures mark delivered and never retry (new SHA = the retry); the per-(rule, target) breaker trips after `BREAKER_LIMIT` consecutive no-clear dispatches and resets only when the condition is observed false. New triggers: add to `AutomationTrigger` in config.ts + a case in `automation-rules.ts` with a documented fire key. Runs dispatch through the same paths keystrokes use, never bespoke ones. Semantics doc: docs/automations.md.
- **Work status is asserted, never inferred-and-stored.** The six-state vocabulary and its rules live in `core/work-status.ts`; the record is `WtSlugState.work`, written only by `wt status` (agents; validation lives in the CLI) and the `u` picker (human; deliberately lenient). Derived signals (session asking, merged/gone) fold in at RENDER/SORT time via `effectiveWorkState`/`rowWorkRank` — never write a derived state into the record. Attention-feed narration comes from diffing wtstate in `useWorkStatusEvents`, not from emit-at-call-site (the writer is usually another process).
- **`log.attention.*` is for "worth interrupting a scan", nothing else.** Status transitions, needs-you signals, escalations. Everything routine stays on `log.event.*` (the firehose); `event.err` already surfaces in the attention view by level, so don't double-emit errors.
- **Freshness is push-based; `r` is a backstop, not the mechanism.** Every external state source has an event trigger that invalidates the matching query — the full trigger inventory is in docs/architecture.md#freshness-model. When adding a state source or mutation path, wire a watcher or an explicit invalidation at the call site rather than shortening a staleTime or telling the user to press `r`; staleTimes only bound how wrong things can be when a trigger is missed.
- **Users update hot from main — every push is a release.** The safety net (docs/updates.md) only works if changes respect its contracts: (1) a shape change to `state.json` (WtState/WtSlugState) bumps `WT_STATE_VERSION` in `core/wtstate/migrations.ts` and adds a forward-only migration — never "just bust" the state file, it's the one non-rebuildable store; (2) persisted-query shape changes bump `CACHE_BUSTER` in `state/client.ts` (busting IS the policy there) — and so does a change of MEANING within an unchanged shape, since a restored entry is indistinguishable from a fresh one (`SyncState.remote` switching from `@{u}` to `origin/<branch>` at v13); (3) config renames get loader aliases + a deprecation warning, new fields get defaults or a copy-pasteable `Errors` message — a config that loaded yesterday must load today; (4) everything under `core/update/` and the `wt rollback` path stays config-free (no imports of config/proc/locks/logger at module load) so the crash-rollback offer works when the config loader itself is what broke; (5) keep `bun run typecheck` + `bun test` green on every push — CI green is what the update gate ships.
- **Pickers follow the shared modal UX rules** (trigger-key re-press confirms, Enter confirms, Esc/q/Ctrl+C cancel, 1–9 quick-pick, sub-affordances get their own letter). The full checklist is docs/architecture.md#modal-ux-rules — hold to it when adding or modifying any picker; deviations fragment the UX.

## Logging & debugging

- Daily app log: `~/.cache/wt/logs/app/wt-YYYY-MM-DD.log` — read it when something looked wrong; event lines are tagged `EVENT` (`grep ' EVENT '` shows what the activity pane showed). Destroy logs: `~/.cache/wt/logs/<slug>-*.log` via `wt logs <slug>`.
- Performance symptoms (machine slow, TUI laggy, runaway CPU/memory) go through the `/perf` skill (`.claude/skills/perf/`) — procedure plus a living notes.md with baseline, open issues, and known failure signatures. Update its notes when perf work teaches something.
- Adding a log call: `createLogger(source)` at module top (or per-call for dynamic slugs). `log.event.X` when the user should see it in the activity pane; `log.debug/info/warn/error` for file-only. `log.error` does **not** auto-promote to the pane.
- **Toasts vs. pane feeds — the contract.** The footer toast is a single latest-wins slot for "see this NOW"; the pane feeds are the record. Keystroke feedback (the flows' `ctx.toast(...)`) is toast-only and never logged — it acknowledges something the user just did. Background code never toasts directly: it rides the logger, where `log.attention.*` toasts by default (attention already means "worth interrupting a scan"; `{toast: false}` opts out) and `log.event.*` opts in with `{toast: true}` — reserved for async completions and failures whose trigger is long past (action finished, handoff sent, automation dispatched/failed, dep sync done). Consequence: every background toast has a pane line behind it, so a missed toast is always recoverable; and routine firehose chatter never toasts.

## Tooling

- Runtime is **Bun**. No node, no pnpm. `bun install`, `bun src/main.ts`.
- Typecheck: `bun run typecheck` (just `tsc --noEmit`).
- Tests are opt-in, not comprehensive: `bun test`. The restack anchor tests (`src/core/stack-ops.test.ts`) pin the squash-safe cut-point logic against real git repos — add cases there when touching `resolveAnchor`. Most other modules have no tests; smoke via the CLI.
- The TUI takes over the terminal — smoke-test refactors via the CLI subcommands (`bun src/main.ts ls`) or check imports with `bun -e 'import("./src/path.tsx")'`.
- **Validate and investigate TUI work with the probe harness, not by reasoning from source.** `scripts/tui-test.sh` drives a REAL wt instance in a throwaway tmux session: `start [name] [w] [h]` (defaults `probe 200x50`, waits for first paint, arms `WT_AUTOMATIONS=off` + `WT_GITHUB=off` so probes never dispatch automations or burn GitHub API quota — PR badges render from the persisted cache), `keys <name> <tmux keys…>`, `snap <name>` / `snap-color <name>` (capture-pane text / SGR colors), `stop <name>` when done. Any change or review touching layout, modals, keys, or colors gets snapshotted through it — at a couple of widths (e.g. 200×50 and 110×30) for layout work. It runs against the real config/state: navigation, pickers, and overlays are fine (Esc out), but never confirm destructive prompts (`d`, `c`, `Ctrl+R`), never press session-attach keys (`F10`/`F11`/`F12`, `;`, `,`, `.`, `m`, `/`) — those hand the probe's terminal to wt's private tmux server and the pane just looks hung — and never press keys that mutate real state without a confirm (`a` archive, `J`/`K` move row, `L` rename, `!` actions: a probe once archived a real row, and a stray `/` cold-started a live agent session). tmux eats a lone `;` (its command separator) — send `'\;'`. Concurrent probes are fine under distinct names. The read-only rules above apply to probes on the REAL config; a sealed second instance (exported `WT_CONFIG` + `WT_TMUX_SOCKET`, relocated `cache_db` — see docs/configuration.md "Running a second isolated instance") may exercise everything, including destructive flows and `WT_GITHUB=on`/`WT_AUTOMATIONS=on`.

## Traps

- **A shape the real board can't show is a fixture away, not an argument.** `scripts/fixture.sh` builds a SEALED instance (own config, own cache root, own `WT_TMUX_SOCKET`, throwaway repo under `$TMPDIR`) whose board carries every shape the renderer branches on — a co-located chain, a fan, a split stack, one row per work status, a dirty row, a commit-less row, a landed pair (clean + dirty) that is the `c` sweep's candidate set: `build`, `probe [name] [w] [h]` (build if needed + start a TUI probe), `wt <args…>` (any wt command against it), `rm`. It drives the working tree's code through public CLI commands only, so it breaks loudly rather than drifting. Reach for it whenever a rendering question can't be answered from the live board — conditional affordances render nothing when their input is absent, which is indistinguishable from broken, and three of four "regressions" reported in one morning were absent inputs. Being sealed, it may exercise anything the read-only rules forbid above. It also configures a real `[dev_server]` on ports 8700+, so `wt dev` and the browser-tab cleanup keyed to the port are exercisable for real. It can't fabricate PR/check/merge-queue badges (they need GitHub), fold state (press Tab), or a stale status (needs age).
- **A guard that needs a record fails OPEN on every row that has no record.** `branchIsMerged`'s vacuous-containment check ("a branch with no commits of its own is not started, never merged") measures against the wtstate fork-base anchor, and `wt new` only wrote one for `--base` forks — so it was inert for every ordinary worktree, which is most of them, and `merged` both closes GitHub issues and feeds the clean sweep. Its only backstop was the first-parent SHA set, a module-level cache five of `fetchOrigin`'s six callers forgot to invalidate. Two independent fail-open paths, same blast radius. When adding a safety check keyed on stored state, ask what it does when the state is missing, and count the population that's in — here it was 12 of 13 rows.
- **"Safe to clean" and "safe to delete" are different questions, and no backend answers the second for you.** `isCleanCandidate` is a claim about the BRANCH (it landed upstream); whether the checkout still holds uncommitted work is independent, and a merged worktree collects new edits the moment anyone reopens a session in it. `d` had the dirty/unpushed guard; the `c` sweep and `wt clean` did not, and passed `force: false` to a backend on the assumption it would refuse — `git worktree remove` does, `rift remove` does not (its `--force` is advisory). Under rift that cost 16 uncommitted files in a merged worktree, unrecoverably: an independent clone's objects, branch and reflog go with the directory, so there is nothing dangling to fsck. The guard is `destroyHazard` in `tui/app-helpers.ts` (shared by `doRemove`, `doCleanRows` and the confirm modal, so the modal's count can't promise a row the sweep will keep) plus the `worktreeIsDirty` filters in `cli/commands/{rm,clean}.ts`. Its "still loading is a hazard, not an absence of one" branch is the load-bearing part. Any new path that removes a checkout consults it; sweeps never force, because forcing is a per-worktree decision.
- **"Unpushed" means "not on `origin/<branch>`" — never anything `@{u}`-derived.** wt points a worktree branch's upstream at its BASE, so every `@{u}` count answers "ahead of base", and both destroy guards were reading it as "would be lost": a fully pushed branch with an open PR refused `wt rm` and got kept by the `c` sweep, telling the human work was at risk when none was. `SyncState.remote` now measures against the branch's own remote ref (which also makes the row's `(…)` group stop duplicating `[…]`, and its help-legend entry true), `pushCounts().unpushed` is the CLI answer, and `localOnlyCommits` in `app-helpers.ts` is the one derivation both TUI paths use. Its fallback carries the other half: with no `origin/<branch>` at all, commits since the base are local-only work UNLESS the branch landed, where the same commits are a squash merge's pre-squash originals. A guard that cries wolf gets forced past by reflex, which costs more than the guard ever saved.
- **`BUN_INSPECT` is inherited by every bun descendant, so opening a session's message socket is not a private act.** wt launches each Claude session under `BUN_INSPECT=ws+unix://…/insp/<tmux name>.sock` (the transport in `core/harness/claude/inject/`), and bun honors that variable in every child: `bun test` run by an agent inside that session tries to bind its parent's socket. On macOS that's a ~20-line EADDRINUSE stack on stderr and the child runs on (the parent's socket survives); the upstream fleet saw the child WIN the path on Linux, so assume the worse behavior. Hence `bin/wt` re-execs under `env -u BUN_INSPECT` and `inject/shims.ts` puts a `bun` shim on each session's PATH. **`claude` is deliberately NOT shimmed**: the session itself launches as bare `claude` through that same PATH, so a shim would strip the variable from the session wt just set it for — silently costing every session its transport, which is exactly how it was found (a live send failing with "no inspector socket").
- **A tmux session's environment comes from the SERVER's birth environment, not from the client that ran `new-session`.** Verified: with a server already up, `FOO=second tmux new-session …` gives the new session `FOO=first` — whatever the process that started the server had. So "my own env already has X, nothing to do" is never a safe inference about what a session wt is creating will see, and only an explicit `env VAR=… cmd` prefix (which `wrapInnerArgs` builds) reliably wins. This is why `pathWithShims()` always emits a full PATH instead of skipping when the shim dir is already present: the skip silently un-shimmed exactly the nested case — wt run by an agent, creating another session — that it existed for.
- **wt usually runs inside a Claude session, so wt's environment is a Claude session's environment.** Anything wt forwards to a session it spawns is inherited from whoever ran wt — and `CLAUDE_CODE_CHILD_SESSION` makes the new session treat itself as a child and **stop writing a transcript**, which is what wt reads for delivery confirmation, status, summaries and the away feed. Started from a shell it looked perfect; started by an agent (i.e. almost always) it silently lost all of it. `wrapInnerArgs` unsets it. Any new "pass the environment through" path asks the same question: whose environment is this, really? The corollary bit twice more: **a stamp that is only ever ADDED is inherited on every branch that doesn't add it.** `WT_AGENT` and `BROWSER_CONTROL_SESSION` are deliberately withheld from some sessions (a human's `F10` shell must not send mail signed as that worktree's agent; a slug-less session owns no browser tabs), and withholding them did nothing at all — the caller's values were already there. Both are now in `wrapInnerArgs`'s unset list, added back only where earned. Note where this hides: `bun test` from a session sees the ambient values, CI does not, so the suite is GREENER in CI than on the machine. Run it inside a session before believing it.
- **The prompt injector's anchors belong to Claude Code, not to us.** `inject/page-routine.ts` walks a live React fiber tree by structural props (`onSubmit` + `messagesRef`/`commands`, `value` + `onChange`). That survives minifier churn but not a restructuring, and a Claude Code update is what would do it. Keep the routine an opaque string ported from upstream rather than idiomatic TypeScript, re-derive it against a live session when it breaks, and never make a change there that `wt claude selftest` (also the `messaging` banner in `wt doctor`) can't confirm.
- **The list panel (`src/tui/panels/list.tsx`) is NOT row-driven.** Different layout (single line of glyphs, no labels), intentionally not wired through `rows/`. Don't try to unify them.
- **Config loads once at module init.** No hot reload — editing the TOML requires restarting `wt`.
- **Remote argv never crosses SSH as raw arguments.** OpenSSH reparses its command through the remote login shell (Fish on the first supported host). Route commands through `core/remote-protocol.ts` + the `_remote` entrypoint; do not interpolate user input into the SSH command string.
- **`Bun.TOML.parse` is built in.** No external TOML lib needed; don't add one.
- **Never park a process on a bare `await new Promise(() => {})`.** With no other pending handle, Bun spins the event loop at 100% CPU instead of blocking (bun 1.3.14; cost a 19h CPU-time burn in a long-lived pane entrypoint). A long-lived idle process needs a real handle to block on — an inert `setInterval`, or `process.stdin.resume()`. Applies to any new `_`-prefixed entrypoint that's meant to just sit there.
- **Never animate through OpenTUI's Timeline engine (`useTimeline`) or `requestAnimationFrame`.** Any playing timeline holds a renderer-wide "live" request: the render loop goes continuous (full tree walk + full repaint per frame, `requestRender()` becomes a no-op so keypresses can't pull a frame forward), and it stays that way until every timeline stops. Two forever-looping timelines in the header wave once kept the app in that mode from boot to quit — ~13% CPU at rest and a standing input-latency tax. Chrome animation goes through the shared ticker in `tui/spinner.tsx` (`useAnimationTick`), which is refcounted and drops to zero frames when nothing animates.
- **A timeout on our own event loop is not evidence about the outside world.** libuv runs the timers phase before the poll phase, so a loop blocked past a deadline fires the timeout callback *ahead of* an IO event that already landed. The dev-server port probe raced a 400ms `socket.setTimeout` against `connect` and reported "nothing is listening" for a live server whenever the TUI stalled (reproduced at 500ms; a 574ms block is in the logs) — the bolt dropped off the row and `s` refused to open a working URL. Any probe of this shape is three-valued: the definitive negative (here `ECONNREFUSED` — on loopback a dead port refuses instantly) means "no", and a timeout means `unknown`, which must never collapse into "no". See `probePort` in `core/dev-server.ts`.
- **macOS-only utilities** (`open`, `pbcopy`, `osascript`, launchd) are assumed. Anything that shells out to them stays guarded by the macOS assumption noted in the README.
- **AppleScript can't take a variable application name.** `tell application X` is resolved at COMPILE time, so a script naming an app that isn't installed fails entirely (a `try` around it doesn't help — compilation precedes execution), and `tell application someVar` won't load the app's terminology, so `tabs`/`URL` come back as syntax errors. The pattern that works is in `core/browser.ts`: filter to RUNNING apps by process name first, then generate one script per app with its name baked in as a literal.
